# 踩过的坑 & 设计反思

> 这套东西是一边做一边趟出来的。把教训记下来，给后来者省时间，也给维护者留心法。

## 工程坑
1. **CLI 丢字段**：`@getnote/cli` 把响应反序列化进固定结构，**静默丢弃未知字段**。录音原文(`audio.original`)、发芽都被它吞了。教训：要拿全数据**直连 raw HTTP**，别只信 CLI 的 JSON 输出。
2. **发芽不在开放 API**：找了一圈开放端点全 404。最后是**反编译 web 应用的 JS bundle**（`home.*.legacy.js`）才发现它走 `notes-api.biji.com` 的内部 API、需网页登录 token。教训：官方没有的，先去 web 应用前端扒接口。
3. **参数名陷阱**：`page_by_note` 的参数是 `single_note_id_str`（大数字用 str 版）不是 `note_id`；`limit` 最大 20，给 50 直接「参数错误」。教训：抓包看 web 应用真实请求（把 CLI 的 base url 指向本地 logging server，看它发什么）。
4. **token 有效期**：web access token 仅 30 分钟，但 refresh_token 约 3 个月。教训：实现自动刷新，否则跑一半就 LoginRequired。
5. **后台任务双开竞态**：`nohup python &` 叠加 harness 的 run_in_background，会起两个进程同时写、竞态。教训：直接用 run_in_background 跑 python 本身，别再加 `&`/nohup。
6. **macOS 权限**：访问 `~/Downloads`/`~/Documents` 需给宿主 App「完全磁盘访问权限」，且**改完必须重启 App** 才生效。
7. **幂等是命根**：所有写操作都要可重复跑不出错——靠「目标已存在则跳过」+ 源侧打标记双重去重。一次竞态跑出两个进程，靠幂等才没出乱子。

## 设计反思（值得保留的判断）
- **单向、只增不改**：只读来源、只新建/移动/追加归档文件、只新增标签；**绝不删除或编辑用户原始资料**。要可逆、要留溯源日志、要能回滚。这是安全底座。
- **分类优先于关键词**：路由先认「类别」这个人意义信号，关键词只用于选子文件夹。否则「内容/创作」这种泛词会把一切吸走。
- **宁可少打标签，不可错打**：判不准的层留空、拿不准的笔记进 staging，而不是硬猜进具体文件夹。敏感内容（医疗/客户/财务）只标记请人复核。
- **元数据驱动 > 死文件夹**：frontmatter（分类/状态/平台/标签）+ Dataview 查询，比僵硬的目录树更耐扩展。
- **把"会变的"单独成库**：标签库、分类、平台、路由规则各自独立成 config，可调用可替换。核心逻辑稳定，个性化在外层。
- **人在回路**：能 100% 确定的自动做（如发芽按 note_id 精确关联）；不确定的出"待确认清单"让人拍板，别替人做不可逆决定。
